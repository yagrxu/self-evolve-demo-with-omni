Agent Self-Evolution

From production traces to an auditable prompt decision

# Bedrock AgentCore  ·  CloudWatch Omni  ·  Strands  ·  CDK const loop = selfEvolve({ mutate: "prompt-only", prove: "held-out" }); # the point is not "can optimize" — it is "can reject a fake optimization" _
the problem
> why --this-demo

A deployed agent isn't good enough.
Can it improve itself — credibly?

# "improve" is easy. "credibly" is the hard part. # Let an LLM rewrite its own prompt, then let an LLM judge the result — # and you most easily get "it looks better on the data you were staring at."

What this demo proves is not "can optimize" — it's "can optimize AND reject a false optimization."

preconditions
> check --prerequisites
Three things must hold at once

Observable

Without it you can't tell where the agent goes wrong in prod. → AgentCore + ADOT → X-Ray / CloudWatch.

Evaluable

Without it "better" is a feeling. → Omni managed evaluators + a custom LLM-judge.

Reproducible

Without it today's gain can't be reproduced tomorrow. → frozen prompt hash / dataset version / scoring semantics / fixed "today".

# Most "auto-optimization" demos do only the first, and leave 2 & 3 to vibes.

omni-self-evolution — SOP
> cat SKILL.md # execute → validate → advance
1 preflight (4 hard prereqs) 2 freeze baseline (hash/model/tools/SHA) 3 harvest traces (read-only) 4 freeze evaluator set + semantics 5 score baseline + name failure modes 6 build eligible set + split
7 generate prompt-only candidates 8 paired replay on control 9 statistical gates (6 gates) 10 confirm winner on holdout 11 decide + write back locally WINNER / NO_CHANGE / NO_DECISION / ROLLED_BACK
steps 1–4 — nail the foundation
> steps 1..4
  • 1Preflight — 4 prereqs, any miss = hard stop: creds · prompts.json model actually live · OMNI_PROMPTS_OVERRIDE works · spans carry prompt version
  • 2Freeze baseline — manifest: prompt version + cross-process-stable hash (blake2b, not built-in hash()) + model + tools + code SHA
  • 3Harvest — pull prod traces local. Read-only is a hard invariant: never write/modify/delete a prod resource
  • 4Freeze evaluators — lock scoring semantics BEFORE first replay. Caught here: Helpfulness real range is [0,6] not [0,1] → wrong range would clamp the whole dimension
steps 5–6 — find the disease, split the data
> steps 5..6

failure modeaffectedagreement

Step 6 gate: eligible ≥12 · control ≥5 · holdout ≥5. First run hit holdout=3 → NO_DECISION. Correct fix: never lower the gate, never re-split — add real traffic (a bigger scenario pool, since re-sending the same dataset keeps the split identical).

step 7 — one change each
> gen-candidates --prompt-only
candidatetargetsmechanism
c1-explicit-constraintsself-contradiction + no alternativeonly ADD constraints
c2-restructured-proceduresame as c1RESTRUCTURE into 4-step procedure
c3-arithmetic-rulescoupon proration errorsadd arithmetic rules only
# each candidate = full copy of baseline, ONLY system prompt content changes (machine-verified). # c1 vs c2 attack the SAME failure mode — "add" vs "restructure" — on purpose, to compare. # no order IDs / expected amounts in a prompt — that memorizes answers, won't generalize.
step 8 — paired replay (must be a script)
> replay --variants 4 --examples 25 --reps 3 # = 300 cells
  • $baseline re-runs live — never reuse historical scores (different traffic/time isn't paired)
  • $variant switches only via OMNI_PROMPTS_OVERRIDE — restart dev server each time (env is process-level)
  • $verify prompt version on every trace — mismatch → discard the cell

# Why not let the agent fire these calls? It's deterministic bookkeeping — a dropped cell doesn't error, it just quietly shifts an arm's mean. The version check literally saved this run: one whole arm (56 cells) was silently mislabeled `v1-draft` until it caught it.

step 9 — six statistical gates
> gates --all-must-pass
gatethresholdwhy
mean quality delta≥ +0.03below = within judge run-to-run noise (~0.02)
paired bootstrap CI95%, lower ≥ 0resample examples → generalization, not "well-measured"
per-evaluator regressioneach ≤ 0.02block "buy the average by trading one dimension"
latency regression≤ 10%a prompt that wins by reasoning longer has a hidden cost
token regression≤ 10%same, on the bill
safetyzero new failureshard gate, not tradeable

# Temptation: nudge the latency gate 10→12% and c2 passes. Discipline: a threshold chosen to admit the candidate in front of you is not a threshold. So we changed the candidate (terse c4) — which crushed the quality gain (+0.0348 → −0.0013). Quality and latency don't separate along "wording."

step 10 — held-out verdict
> cat gates-holdout.json # the single most important page
c2 on control:  Δ +0.0348   CI [+0.015, +0.056]  ← looked real c2 on holdout:  Δ −0.0018   CI [−0.054, +0.058]  ← gain gone               PolicyGrounding −0.1296  ← a dimension control never exposed

If we'd relaxed the latency gate and shipped c2, we'd have deployed a worse prompt — with control showing all green. The held-out set, not any threshold, stopped it.

step 11 — four decisions, must distinguish
> decide
decisionmeaningthis run
WINNERpassed all gates + holdout confirm—
NO_CHANGEmeasured, nobody won. baseline stands✓ this run
NO_DECISIONcouldn't measure (too few samples / no traces)Phase 4 hit it once

# NO_CHANGE ≠ NO_DECISION — "measured, no winner" vs "couldn't measure." Conflating them lets an unmeasured run read as a validated baseline. This NO_CHANGE is a successful run: it proved, reproducibly, these prompt-only hypotheses don't beat baseline.

human-in vs human-on the loop
> discuss --governance

Human IN the loop

Inside every step; the system waits for a nod. Co-pilot, hands on the wheel.
+ every decision endorsed   − slow, doesn't scale

Human ON the loop

Outside the loop; the system runs, human supervises outcomes. On-call watching dashboards.
+ scalable, fast   − system may auto-do wrong things

Not either/or. Mature automation picks a different mode per stage.

where the line sits in this demo
> loop --who-decides-what

HUMAN ON THE LOOP — runs unattended

Step 3 harvest → 5 failure modes → 7 candidates → 8 replay → 9 gates → 10 holdout. Produces auditable evidence and a recommendation. No human in any step.

HUMAN IN THE LOOP — must nod

Whether to ship a WINNER (Invariant 3: the SOP never deploys itself) · whether to waive a gate (--waive-gate, reason required).

# The analysis is on-the-loop; the exit (ship, waive) is in-the-loop — those decisions have a prod blast radius the SOP can't assess.

three mechanisms enforce the line
> how --enforced

Read-only + no deploy

Never writes a prod resource, never cdk deploy / publish. It emits a recommendation, not an action.

Auditable waiver

--waive-gate: threshold unchanged, gate still ❌, reason logged to JSON, verdict WINNER_BY_HUMAN_WAIVER. c2's waived latency didn't wash out its holdout quality fail.

Holdout: auto, not waivable

Overfitting detection is NOT left to human judgement — people believe the candidate they want. Split by stable hash before candidates exist.

what this really proves
> summary
# NOT "an AI can auto-optimize a prompt" (too easy, not credible) What a self-optimizing loop that can reject a fake optimization looks like:   › read-only, no deploy, prompt-only   › every number reproducible, every gate justified, every waiver logged   › holdout auto-blocks overfitting; humans make the value calls

Reject-capable is ship-ready.

# Let humans make value judgements; let the machine guard against self-deception.
