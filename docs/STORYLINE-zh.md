## 引子:一个不太好用的客服,能不能自己变好?

我们有一个已经上线的电商退货客服 agent,效果不理想。最自然的想法是:让它自己进化——让 AI 改自己的提示词(prompt),再让 AI 判断改得好不好。

但这里有个陷阱。"让它变好"其实很容易,难的是**让人相信它真的变好了**。你让一个大模型改自己的 prompt,再让另一个大模型来打分,最容易得到的结果是:"在你刚好盯着看的那批数据上,它看起来变好了"。这几乎一定会发生,而且骗过的是你自己。

所以这个 demo 要证明的,**不是"AI 能自动优化",而是"一个能拒绝掉假优化的自动优化循环长什么样"**。能发现改进不稀奇,能在一个看起来变好、实则没变好的候选面前说"不",才是敢把自动优化接进生产的前提。

要做到这点,有三件事必须同时成立:第一,**可观测**——不然你根本不知道 agent 在生产里哪里错了;第二,**可评估**——不然"更好"只是一种感觉;第三,**可复现**——不然今天测出的提升,明天复现不出来。很多"AI 自动优化"的演示只做到了第一件,把第二三件交给了直觉。我们三件都做实:agent 跑在 Bedrock AgentCore 上,用 ADOT 自动埋点把 trace 送进 X-Ray 和 CloudWatch;评估用 CloudWatch Omni 的托管评估器加一个自建的裁判;而 prompt 的哈希、数据集的版本、评分的口径、甚至"今天是哪天"这些全部冻结,保证每个数字都能重放出来。整条基础设施——agent、评估器、在线评估——都用 CDK 声明式部署,一条命令拉起来,不用手点控制台。

**起点是一个故意做弱的 agent**:它的系统提示只有一句话——"友好、简洁地回答,让用户满意"。它弱在哪是精心设计的:没要求查政策、没给工具调用规矩、没给算钱的规则、没要求"不能退的时候给个替代方案"。每一处缺陷,都对应一个能被评估器抓住的失败模式。

## 第一幕:为什么选退货客服这个场景

场景是电商订单的退货客服。选它是因为**答案能被精确验证**——退多少钱是有唯一正确数字的,不像开放聊天那样只能凭感觉,这样才能做严格评估。

业务规则故意做得很绕:五个商品类目(电子、服饰、图书、家居、生鲜),每类的退货窗口、手续费比例、运费谁承担都不一样;再加三条横跨所有类目的规则——优惠券按原价比例分摊、原运费什么时候退、破损商品的特殊处理。规则复杂到:模型不老老实实查工具、光靠常识,一定答错。

我准备了 55 个测试订单,切成**三份完全不重叠**的数据集:`dev_local`(15 条)本地开发调试用,`prod_sim`(20 条)模拟生产流量,`verify`(20 条)锁到最后做最终验证、全程不让模型碰。招牌难题是订单 ORD-10012:一单里买了好几样、用了优惠券,用户只退一个手机壳,正确答案是 **¥44.88**,要先把券按原价比例摊、再按"只退一件"拆、再扣手续费,三步都对才算对。

还有一个容易被忽略但很关键的设计:所有标准答案(oracle)不是人手写的,而是用 agent 自己那套算钱的纯函数直接生成的。因为优惠券分摊这种算术,人手写几乎必错,而**一个错的标准答案会让评估器把对的判成错、错的判成对,污染整条评估链**。用代码生成真值,就把这个隐患堵死了。

## 第二幕:整个循环长什么样

整套流程分六个阶段,首尾相接成一个闭环:Phase 1 做出弱 agent 并接好埋点;Phase 2 在本地跑多维评估拿到基线;Phase 3 部署上云、打真实流量、在线评估;Phase 4 把表现差的 trace 导出来;Phase 5 是核心——生成候选、A/B 重放、过统计门禁、再用留出集确认;只有产出一个真正的赢家,才回到 Phase 6 重新部署、用第三份数据验证。

这个循环的**入口是生产 trace,出口是四选一的决策**。而且有一条铁律贯穿始终:**整个循环里只有 prompt 能改**,模型、工具、代码、评估器、数据集全部冻结——否则测出的差异就没法归因到 prompt 头上。

三份数据集其实是三层防线:`control`(控制集)是允许反复看、反复调的;`holdout`(留出集)只在第 10 步看那一次,专门抓过拟合;`verify` 连 holdout 都算被"污染"了,是留到最上层的最干净的一批。数据切分用 `scenario_id` 的 blake2b 哈希——是个**纯函数**,重跑得到一模一样的切分。这不是洁癖:如果用随机切分,你可以反复重摇直到某个候选恰好通过,而最终报告里看不出任何异常。

**先剧透结局:最终判决是 `NO_CHANGE`(维持原状)。** 四个 prompt 候选、486 次配对重放,没有一个确立了能泛化的提升。其中候选 c2 在控制集上看着像赢了(质量 +0.0348,置信区间全在正区间),结果被留出集揭穿是过拟合。但这**不是**一个失败的 demo——恰恰相反,能拒绝一个假优化,正是这套方法论的价值所在。

## 第三幕:CloudWatch Omni 到底用到了什么

Omni 提供 16 个工具。这一页把 16 个全列出来,并标了颜色:**9 个深度使用**(check_credentials 检查凭证、configure_omni 接线、setup_skills 装技能、manage_local_collector 本地采集器、local_server 本地服务、manage_test_agent 调用 agent、search_local_telemetry 找 trace、manage_datasets 管数据集和版本、manage_evaluations 打分和自建裁判);**3 个走了替代通路**(云端 trace 查询那三个因为本机一个 region/DNS 问题连不上,我们直接用 boto3 从 CloudWatch Logs 读同样的结果——效果一样,还能进 CI);**4 个没用到**(都是 IDE 交互和可视化增强,跟自动化循环无关)。

评估器方面,Omni 自带 20 多个托管评估器,分三个层级:TRACE 级看单次回答(正确性、忠实度、有用性、指令遵循等),TOOL_CALL 级看工具用得对不对,SESSION 级看整段会话的目标达成。我们还**自建了一个叫 PolicyGrounding 的裁判**。为什么要自建?因为内置的"正确性"只看最后那个数字对不对,"指令遵循"只看它有没有照系统提示做——可 v1 的提示压根没要求查政策,所以它"遵循得很好"却答得很错。PolicyGrounding 问的是一个正交的问题:**回答里的政策数值,到底是从工具返回里来的,还是模型编的?**

整条评估管道都进了 CDK:Runtime、自定义 Evaluator、100% 采样的在线评估配置、trace 投递管道。就一行 `tracingEnabled: true` 换来整条投递链路;改了 prompt,资源哈希变、runtime 出新版本、endpoint 自动跟上。评估器和持续评估跟 agent 一起部署,不用手工点控制台——这对可追溯性很关键。

## 第四幕:循环里到底怎么走的(方法论 SOP 的 11 步)

**第 1 到 4 步是把地基钉死。** 第 1 步预检四个硬前提,缺一个就停:凭证能用、prompts.json 里的模型是真生效的(不是摆设)、变体切换开关能用、trace 上真的带着 prompt 版本。第 2 步冻结基线,写下 prompt 版本、跨进程稳定的哈希(用 blake2b,不用语言内置的 hash,因为它跨进程会变)、模型、工具、代码 SHA。第 3 步只读地把生产 trace 拉到本地——只读是铁律,绝不写、改、删任何生产资源。第 4 步**在第一次重放之前**冻结评估器和它们的打分口径。就是在这步我抓到一个坑:Helpfulness 的真实分值范围是 0 到 6,不是我以为的 0 到 1——如果不核对,归一化会把整个维度的分数压平,失去分辨力。

**第 5、6 步是找病根、切数据。** 第 5 步给基线打分、把低分归类成失败模式。结果三个独立来源(本地基线、云上评估、导出分类)一致指向同一个病根:**Helpfulness 全军覆没,31 条里 31 条不及格,本地和云上及格率都是 0%**。第 6 步建合格样本集并切分,门槛是合格样本≥12、控制集≥5、留出集≥5。第一次跑的时候留出集只有 3 条,不够,判了 `NO_DECISION`(无法判定)。正确的应对是:**绝不降门槛、绝不重切**,只能去补真实流量——而且对同一份数据再打一遍没用,切分不会变,得扩大场景池本身。

**第 7 步生成候选,每个只改一件事。** c1 只往提示里"加约束",c2 把提示"重构成一套四步流程",c3 只加算钱规则。每个候选都是基线的完整拷贝、只改系统提示那一段(机器校验过)。c1 和 c2 故意打同一个病根、一个"加"一个"改",就是为了比较哪种手段更有效。提示里绝不写具体订单号或期望金额——那等于把答案背进去,不会泛化。

**第 8 步是配对重放,而且必须是脚本、不能让 agent 自己发。** 4 个变体 × 25 个样本 × 重放 3 遍 = 300 次。三条硬规矩:基线必须现场重跑(不能复用历史分数,不同时间不同流量不构成配对);变体只能靠环境变量切换、每次都重启服务(否则进程里还是上一个变体);每次调用都要核对 trace 上的 prompt 版本,不对就丢掉这一格。为什么不让 agent 自己跑循环?因为这是确定性的记账,漏一格不会报错,只会让某个变体的均值悄悄偏掉。而这条版本核对规矩,在真跑时确实救了场——有整整一个变体(56 格)被悄悄标错成了 v1-draft,是它抓住的。

**第 9 步是六道统计门,全过才算赢:** 质量提升要 ≥ +0.03(低于这个就落在裁判自己的抖动范围里了);配对 bootstrap 的 95% 置信区间下界要 ≥ 0(对样本重采样,问的是"能不能泛化到新输入",而不是"这批测得准不准");每个单项评估器的回退不能超过 0.02(防止"靠牺牲一个维度换平均分");延迟回退 ≤ 10%(靠更长推理赢来的提升,代价没算在质量分里);token 回退 ≤ 10%(同样的道理,这次是账单);安全项零新增失败(硬门,不可交易)。

**第 9 步的结果:一次"差一点点"的近失。** c1 质量没够、区间下界还是负的;c3 好几项都没过;而 **c2 质量门过了(+0.0348)、置信区间也全在正区间**,只在延迟这一项上以 11.11% 超了 10% 的线——就差 1.11 个百分点。这里有个诱惑:把延迟门从 10% 松到 12%,c2 就过了。但纪律是:**一个为了放行眼前候选而临时选的门槛,就不是门槛了。** 所以我改的是候选、不是标尺——做了个精简版 c4,结果质量提升被压没了(从 +0.0348 掉到 −0.0013)。这说明:质量和延迟在"改措辞"这条路上是分不开的。

**第 10 步,留出集给出裁决——这是全场最关键的一页。** 同一个 c2,在控制集上质量 +0.0348、区间漂亮;换到从没调过的留出集上,质量塌成 **−0.0018**,置信区间跨越零点,而且在一个控制集上从没暴露过的维度(PolicyGrounding)上**回退了 0.13**。翻译过来:**如果当初真把延迟门放松、让 c2 上线,我们会部署一个实际更差的 prompt,而控制集的报告会一路显示绿灯。是留出集、而不是任何阈值调整,把它拦了下来。**

**第 11 步出决策,四种结局必须区分清楚:** WINNER(过了所有门、留出集也确认);NO_CHANGE(测了,但没人赢,维持原状);NO_DECISION(根本没测成,比如样本不够);ROLLED_BACK_LOCAL(本地写回后又回退)。**NO_CHANGE 和 NO_DECISION 绝不能混**——一个是"测过了没赢",一个是"根本没测成",混起来就会让一次没测成的运行被当成"基线已验证"。这次的 NO_CHANGE 是一次**成功**的运行:它用可复现的证据证明了,这几个 prompt 层面的假设都赢不过基线,下一步得换机制(比如把替代方案的判断挪到工具层),而那已经超出"只改 prompt"的范围了。

## 第五幕:人在环里,还是人在环上?

最后聊治理。有两种模式:**Human in the loop(人在环内)**——人夹在每一步里,系统等人点头才继续,像手把手的副驾,好处是每个决定都有人背书,代价是慢、不可扩展;**Human on the loop(人在环上)**——人在循环之外,系统自己跑、人监督结果,像看仪表盘的值班工程师,好处是快、可扩展,代价是系统可能自动做错事。这不是二选一,**成熟的自动化是在不同环节选不同的模式**。

这个 demo 里的分界很清楚:**分析和评估部分是"人在环上"**——从拉 trace、归纳失败、生成候选、重放、过门、到留出集确认,整段无人干预,产出的是带证据的建议。**而循环的出口是"人在环内"**——是否上线赢家(SOP 有条铁律:它绝不自己部署)、是否人工豁免某道门,这些决定有生产级的爆炸半径,SOP 评估不了,必须人来拍板。

有三个机制把这条界落到实处:第一,**只读、不部署**——SOP 全程不碰生产资源、绝不 deploy,它只产出建议、不产出行动;第二,**可审计的豁免**——当有人决定放行某道门,阈值一个字都不改、门照样记为不通过、豁免连同理由写进 JSON、结局单独记成"人工豁免通过",绝不伪装成自动通过(这次实测里,即便豁免了 c2 的延迟门,它的质量门在留出集上照样没过,豁免没能把它洗白);第三,**留出集是自动的、不可豁免的**——过拟合检测坚决不交给人判断,因为人会倾向于相信自己想要的那个候选;它由稳定哈希在候选诞生之前就切好,人事后动不了。

一句话收尾这部分:**让人做价值判断(6 秒变 6.6 秒值不值,这种权衡人擅长),让机器防自欺(这个提升是真的还是过拟合,这种事人会被沉没成本带偏,交给冻结的门和留出集)。**

## 尾声:真正的成果是那份可复用的 Skill

最后要强调:这个 demo 留下的**不是一套演示脚本,而是一份可复用、已入库的方法论**——`.kiro/skills/omni-self-evolution/SKILL.md`(同时也放在 `.claude/skills/omni/self-evolution/`)。它是一份 459 行的程序化 SOP:11 个步骤、6 条硬不变量、6 道统计门、4 种决策,把上面讲的所有纪律都写成了"执行 → 验证 → 才能前进"的可执行约束。

而**本次这整个 demo,就是它的验证案例**——不是"我们相信这套方法有效",而是"这套方法被端到端真跑了一遍":它真的产出了 `NO_CHANGE`,它的留出集这一步真的抓住了 c2 的过拟合,它的版本核对真的拦下了一个被标错的变体。方法论不是被断言出来的,是被行使(exercised)出来的。

所以对听众而言,最该带走的不是这几张 slide,而是那份 skill:**换一个项目,把它拿过去,同样能跑。一份能复用的 skill,胜过一页能欣赏的 slide。**

---

## 结语

这个 demo 真正证明的,不是"AI 能自动改 prompt"(那太容易,也不可信),而是**一个能拒绝假优化的自动优化循环该长什么样**:只读、不部署、只改 prompt;每个数字可复现、每道门有论证、每次豁免留痕;留出集自动挡过拟合,人只做价值判断。

**能拒绝,才敢自动。** 这是把 agent 自我进化接进生产的前提。
